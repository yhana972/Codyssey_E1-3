# Mini NPU Simulator

Python의 반복문을 이용해 MAC(Multiply-Accumulate) 연산을 직접 구현하고,
입력 패턴과 필터의 점수를 비교하여 패턴을 판정하는 콘솔 기반 NPU 시뮬레이터입니다.

외부 수치 연산 라이브러리 없이 Python 표준 라이브러리만 사용했으며,
3×3, 5×5, 13×13, 25×25 행렬의 MAC 연산 시간을 측정하여
행렬 크기와 연산량의 관계도 함께 분석합니다.

---

# 1. 이 미션을 왜 하는가?

AI 연산에서는 많은 수의 **곱셈과 덧셈**이 반복적으로 수행됩니다.

이때 자주 등장하는 연산 중 하나가 **MAC(Multiply-Accumulate)** 입니다.

MAC의 기본 구조는 다음과 같습니다.

```text
값을 곱한다(Multiply)
        ↓
결과를 기존 값에 더한다(Accumulate)
        ↓
이 과정을 반복한다
```

예를 들어 입력 패턴과 필터가 있다면 같은 위치의 숫자를 서로 곱하고,
그 결과를 모두 더해서 하나의 점수를 만들 수 있습니다.

```text
입력 Pattern
      +
Filter
      ↓
같은 위치 값끼리 곱하기
      ↓
모든 곱셈 결과 더하기
      ↓
MAC Score
      ↓
여러 Filter의 Score 비교
      ↓
패턴 판정
```

NPU는 실제로 훨씬 복잡하고 많은 연산을 병렬로 처리하지만,
이번 미션에서는 그 기반이 되는 반복적인 곱셈·누적 연산을 Python으로 직접 구현하여
MAC의 원리와 연산량 증가를 이해하는 것을 목표로 했습니다.

> 이 프로젝트는 실제 NPU 하드웨어를 구현하는 프로젝트가 아니라,
> NPU 연산의 기초가 되는 MAC 연산을 단순화하여 학습하기 위한 시뮬레이터입니다.

# 4. MAC 연산 설명

MAC는 **Multiply-Accumulate**의 약자입니다.

같은 위치에 있는 두 값을 곱하고 그 결과를 계속 더합니다.

예를 들어:

```text
Pattern          Filter

1  2             5  6
3  4             7  8
```

라면 다음을 계산합니다.

```text
(1 × 5)
+ (2 × 6)
+ (3 × 7)
+ (4 × 8)
```

코드에서는 다음과 같이 구현했습니다.

```python
score = 0.0

for row in range(size):
    for col in range(size):
        score += pattern[row][col] * filter_data[row][col]
```

---

## 왜 NumPy를 사용하지 않았는가?

실무에서는 NumPy 등을 사용하면 행렬 연산을 훨씬 간단하고 빠르게 처리할 수 있습니다.

하지만 이번 미션에서는 MAC 연산이 실제로:

```text
위치 접근
→ 곱셈
→ 누적
```

되는 과정을 직접 이해하기 위해 Python 반복문으로 구현했습니다.

# 5. 데이터 검증

MAC 연산을 하기 전에 행렬이 정상적인지 확인합니다.

## 왜 정사각형 검증이 필요한가?

정상적인 3×3 행렬은 다음과 같습니다.

```text
1 0 1
0 1 0
1 0 1
```

모든 행에 3개의 값이 있습니다.

반면:

```text
1 0
0 1 0
1 0 1
```

처럼 행마다 값의 개수가 다르면 정상적인 N×N 행렬이 아닙니다.

`validate_matrix()`에서는 다음을 확인합니다.

1. 빈 배열인지 확인
2. 행의 개수 N 확인
3. 모든 행의 열 개수가 N인지 확인

---

## 왜 `validate_matrix()`와 `validate_same_size()`를 따로 만들었는가?

다음 두 행렬은 각각 정상적인 정사각형일 수 있습니다.

```text
Pattern : 5×5
Filter  : 13×13
```

하지만 서로 크기가 다르기 때문에 MAC 연산에 함께 사용할 수 없습니다.

즉 검증은 두 종류가 필요합니다.

```text
1. 배열 자체가 정상적인 N×N인가?
   → validate_matrix()

2. 두 배열의 크기가 서로 같은가?
   → validate_same_size()
```

JSON 모드에서는 추가로:

```text
pattern key = size_13_1
```

인데 실제 패턴 데이터도 정말 `13×13`인지 확인합니다.

# 6. 라벨 정규화 정책

JSON 데이터에서는 같은 의미가 서로 다른 문자열로 표현될 수 있습니다.

```text
Filter 이름
cross
x

Expected
+
x
```

반면 프로그램 내부의 판정 결과는:

```text
Cross
X
```

를 사용합니다.

그대로 비교하면:

```python
"Cross" == "+"
```

는 `False`입니다.

따라서 비교 전에 라벨을 다음과 같이 통일합니다.

| 외부 데이터 | 내부 표준 |
|---|---|
| `+` | `Cross` |
| `cross` | `Cross` |
| `x` | `X` |

```python
label_map = {
    "+": "Cross",
    "cross": "Cross",
    "x": "X",
}
```

---

## 왜 `normalize_label()`이 필요한가?

외부 데이터가 항상 프로그램 내부의 표현 규칙을 따른다는 보장은 없습니다.

따라서:

```text
외부 표현
   ↓
정규화
   ↓
내부 표준 표현
```

과정을 거칩니다.

이렇게 하면 이후의 판정 코드에서는 외부 데이터가 `+`였는지 `cross`였는지
신경 쓰지 않고:

```text
Cross
X
```

만 사용하면 됩니다.

# 7. 동점 판정 정책

두 MAC 점수의 차이가 매우 작다면 다음 조건으로 동점 처리합니다.

```python
abs(score_a - score_b) < 1e-9
```

조건을 만족하면:

```text
UNDECIDED
```

를 반환합니다.

---

## 왜 `abs()`를 사용하는가?

두 값을 빼는 순서에 따라 결과는 음수가 될 수 있습니다.

```text
1 - 2 = -1
2 - 1 =  1
```

하지만 동점 여부를 확인할 때 중요한 것은:

> 어느 값이 더 큰가?

가 아니라:

> 두 값 사이의 거리가 얼마나 작은가?

입니다.

따라서:

```python
abs(score_a - score_b)
```

처럼 절대값을 사용합니다.

---

## `1e-9`는 무엇인가?

`1e-9`는 과학적 표기법입니다.

```text
1e-9
=
0.000000001
```

즉 두 점수의 차이가 `0.000000001`보다 작다면
이번 프로젝트에서는 사실상 같은 값으로 판단합니다.

---

## 왜 `score_a == score_b`를 사용하지 않았는가?

Python의 `float`는 실수를 컴퓨터 내부에서 2진수로 표현합니다.

일부 10진수 소수는 2진수로 정확하게 표현할 수 없기 때문에
가장 가까운 표현 가능한 값으로 저장됩니다.

대표적인 예:

```python
0.1 + 0.2
```

결과가 정확히:

```text
0.3
```

이 아니라:

```text
0.30000000000000004
```

처럼 나타날 수 있습니다.

이를 **부동소수점 오차**라고 합니다.

이번 데이터에서도 다음처럼 사실상 같은 점수가
아주 미세하게 다르게 계산될 수 있습니다.

```text
0.9
0.8999999999999999
```

이를 단순히 크기로만 비교하면 한쪽이 더 큰 것으로 판정될 수 있습니다.

---

## 왜 하필 `1e-9`인가?

`1e-9`는 모든 프로그램에서 반드시 사용해야 하는 절대적인 기준이 아닙니다.

허용 오차는:

- 데이터의 크기
- 요구되는 정밀도
- 문제 조건

에 따라 달라질 수 있습니다.

이번 미션에서는 매우 작은 부동소수점 차이 때문에
Cross 또는 X가 선택되는 것을 방지하기 위한 **동점 판정 정책값**으로
`1e-9`를 사용했습니다.

즉:

```text
1e-9 = Python float의 절대적인 오차 한계
```

가 아니라:

```text
이번 프로그램에서 사용하는 비교 허용 범위
```

라고 이해하는 것이 정확합니다.

# 9. FAIL 원인 분석

FAIL이 발생한 경우 단순히 개수만 기록하지 않고,
각 케이스가 왜 실패했는지를 함께 분석합니다.

가능한 실패 원인은 크게 다음 세 종류로 나눌 수 있습니다.

```text
1. 데이터 구조 문제
2. 행렬 크기 문제
3. MAC 판정 결과와 expected 불일치
```

---

## 데이터 구조 문제

예:

```text
input 없음
expected 없음
해당 크기의 Filter 없음
Cross 또는 X Filter 없음
```

이 경우 MAC 계산 자체를 수행할 수 없기 때문에
해당 케이스를 FAIL로 기록합니다.

---

## 행렬 크기 문제

예:

```text
Pattern : 5×5
Filter  : 13×13
```

또는:

```text
key = size_13_1
실제 Pattern = 5×5
```

같은 경우입니다.

MAC 연산 전에 검증하여 잘못된 데이터로 인한 오류를 방지합니다.

---

## 판정 결과 문제

예:

```text
Cross Score ≈ X Score
```

인 경우 epsilon 정책에 의해:

```text
UNDECIDED
```

가 발생할 수 있습니다.

하지만 JSON의 예상 정답이:

```text
Cross
```

또는:

```text
X
```

라면 예상 정답과 다르기 때문에 FAIL로 처리됩니다.

---

## FAIL이 코드 오류라는 뜻인가?

반드시 그렇지는 않습니다.

예를 들어:

```text
Cross Score = 0.9
X Score     = 0.8999999999999999
```

이면 두 값의 차이는 매우 작습니다.

현재 프로그램의 정책:

```python
abs(score_a - score_b) < 1e-9
```

을 만족한다면 의도적으로 `UNDECIDED`를 반환합니다.

따라서 이 경우 FAIL은:

```text
프로그램이 잘못 계산함
```

이 아니라:

```text
현재 동점 판정 정책과 expected가 일치하지 않음
```

으로 분석해야 합니다.

# 10. 성능 측정 방법

성능 측정에는 Python 표준 라이브러리의:

```python
time.perf_counter()
```

를 사용했습니다.

측정 방식:

```text
측정 시작
   ↓
calculate_mac() 10회 실행
   ↓
측정 종료
   ↓
총 시간 계산
   ↓
10으로 나누기
   ↓
MAC 1회 평균 시간
   ↓
초 → 밀리초 변환
```

---

## 왜 `time.perf_counter()`를 사용했는가?

MAC 함수는 실행 시간이 매우 짧습니다.

따라서 짧은 코드 실행 구간의 경과 시간을 측정하는 데 적합한
`time.perf_counter()`를 사용했습니다.

---

## 왜 한 번이 아니라 10번 실행하는가?

한 번만 측정하면 실행 당시의:

- 운영체제 스케줄링
- CPU 상태
- 실행 중인 다른 프로그램

등의 영향을 많이 받을 수 있습니다.

따라서 동일한 MAC 연산을 최소 10회 반복하고:

```text
총 실행 시간 / 반복 횟수
```

를 사용하여 평균 실행 시간을 계산했습니다.

10회는 이번 미션의 최소 측정 기준이며,
보다 정밀한 벤치마크에서는 더 많은 반복 측정이 필요할 수 있습니다.

---

## 왜 `print()`와 파일 읽기 시간은 제외했는가?

이번 성능 비교의 대상은:

```text
행렬 크기에 따른 MAC 계산 시간
```

입니다.

측정 구간에:

```text
JSON 파일 읽기
print()
input()
```

까지 포함하면 MAC과 관계없는 I/O 시간이 섞이게 됩니다.

따라서 실제 측정 구간에는:

```python
calculate_mac()
```

만 포함했습니다.

# 12. 왜 N×N의 연산량은 N²인가?

MAC 함수는 다음 구조로 동작합니다.

```python
for row in range(size):
    for col in range(size):
        ...
```

바깥 반복문이 N번 실행되고,
그 안에서 다시 N번 실행됩니다.

따라서:

```text
N × N
=
N²
```

개의 위치를 처리합니다.

| 행렬 크기 | N² 연산량 |
|---|---:|
| 3×3 | 9 |
| 5×5 | 25 |
| 13×13 | 169 |
| 25×25 | 625 |

따라서 현재 MAC 구현의 시간 복잡도는:

```text
O(N²)
```

입니다.

---

## N이 두 배가 되면 연산량도 두 배인가?

아닙니다.

예를 들어:

```text
N = 5
→ 25개 위치

N = 10
→ 100개 위치
```

N은 2배가 되었지만 처리해야 하는 위치는 4배가 됩니다.

즉 행렬의 크기가 커질수록 연산량은 제곱에 비례하여 증가합니다.

---

## 실제 실행 시간도 정확히 N² 비율로 증가하는가?

반드시 그렇지는 않습니다.

실제 실행 시간은:

- Python 인터프리터
- CPU 캐시
- 운영체제 스케줄링
- 현재 시스템 부하

등의 영향을 받습니다.

따라서:

```text
N² 증가
→ 필요한 연산량 증가
```

는 확실하지만:

```text
N²이 4배
→ 실행시간도 정확히 4배
```

라고 단정할 수는 없습니다.

실제 측정값과 이론적인 N² 연산량을 함께 비교하는 이유가 여기에 있습니다.

# 15. 구현하면서 이해한 핵심 내용

1. MAC은 같은 위치의 값을 곱하고 그 결과를 계속 누적하는 연산이다.
2. 하나의 `calculate_mac()` 함수로 3×3, 5×5, 13×13, 25×25를 모두 처리할 수 있다.
3. 행렬 크기를 코드에 직접 고정하지 않고 `len(pattern)`을 사용하여 N을 얻도록 구현했다.
4. 계산 전에 행렬 자체가 정상적인 N×N 구조인지 확인해야 한다.
5. 각각 정상적인 정사각 행렬이어도 서로 크기가 다르면 함께 MAC 연산을 할 수 없다.
6. 외부 데이터의 표현 방식과 프로그램 내부 표현 방식이 다를 수 있으므로 라벨 정규화가 필요하다.
7. 부동소수점 계산에서는 수학적으로 같은 값도 매우 작은 차이가 발생할 수 있다.
8. 따라서 단순한 `==` 비교 대신 epsilon 기반 비교를 적용했다.
9. `1e-9`는 절대적인 float 오차 기준이 아니라 이번 프로그램의 동점 판정 정책값이다.
10. 성능 비교에서는 파일 읽기와 출력 시간을 제외하고 MAC 자체의 연산 시간만 측정해야 한다.
11. 한 번의 측정보다 여러 번 반복한 뒤 평균값을 사용하는 것이 실행시간 변동의 영향을 줄일 수 있다.
12. N×N MAC은 N²개의 위치를 확인하므로 시간 복잡도는 `O(N²)`이다.
13. 3×3, 5×5, 13×13, 25×25의 연산 위치 수는 각각 9, 25, 169, 625이다.
14. 실제 실행시간은 이론적인 N² 연산량뿐만 아니라 실행 환경에도 영향을 받는다.
15. 계산, 검증, 판정, 성능 측정, 출력을 역할별 함수로 분리하면 여러 실행 모드에서 동일한 코드를 재사용하기 쉽다.
