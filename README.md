# Mini NPU Simulator

Python 반복문으로 MAC(Multiply-Accumulate) 연산을 직접 구현하고, 입력 패턴과 필터의 점수를 비교하여 패턴을 판정하는 콘솔 기반 Mini NPU Simulator입니다.

외부 수치 연산 라이브러리 없이 Python 표준 라이브러리만 사용했으며, 3x3, 5x5, 13x13, 25x25 행렬의 MAC 연산 시간과 N^2 연산량을 함께 비교합니다.

---

# 1. 프로젝트 목적

AI 연산에서는 곱셈과 덧셈이 매우 많이 반복됩니다. 그중 기본이 되는 연산이 MAC입니다.

```text
Multiply  : 같은 위치의 값을 곱한다
Accumulate: 곱한 결과를 계속 더한다
```

입력 패턴과 필터가 있을 때 같은 위치의 숫자를 곱하고, 모든 결과를 더하면 하나의 MAC Score가 됩니다. 여러 필터에 대해 MAC Score를 계산한 뒤 더 높은 점수를 가진 필터를 선택하면 입력 패턴이 어떤 형태에 가까운지 판정할 수 있습니다.

이 프로젝트는 실제 NPU 하드웨어를 구현하는 것이 아니라, NPU 연산의 기초가 되는 MAC 구조를 Python 코드로 직접 구현하며 연산량과 실행 시간의 관계를 이해하기 위한 학습용 시뮬레이터입니다.

# 7. MAC 연산 설명

MAC는 Multiply-Accumulate의 약자입니다. 같은 위치에 있는 두 값을 곱하고, 그 결과를 계속 더하는 연산입니다.

예를 들어 다음 두 행렬이 있습니다.

```text
Pattern          Filter

1  2             5  6
3  4             7  8
```

MAC 계산은 다음과 같습니다.

```text
(1 * 5) + (2 * 6) + (3 * 7) + (4 * 8)
= 5 + 12 + 21 + 32
= 70
```

코드에서는 다음 구조로 구현했습니다.

```python
score = 0.0
size = len(pattern)

for row in range(size):
    for col in range(size):
        score += pattern[row][col] * filter_data[row][col]
```

NumPy 같은 외부 라이브러리를 사용하면 행렬 연산을 더 간단하게 작성할 수 있지만, 이번 미션에서는 MAC이 내부적으로 어떻게 반복되는지 이해하기 위해 Python 반복문으로 직접 구현했습니다.

# 8. 데이터 검증

MAC 연산을 수행하기 전에 패턴과 필터가 정상적인 N x N 행렬인지 검증합니다.

## 8.1 N x N 행렬 검증

정상적인 3x3 행렬은 모든 행에 3개의 값이 있어야 합니다.

```text
1 0 1
0 1 0
1 0 1
```

반면 다음 데이터는 행마다 열 개수가 다르므로 올바른 N x N 행렬이 아닙니다.

```text
1 0
0 1 0
1 0 1
```

`validate_matrix()`는 다음을 확인합니다.

1. 빈 배열이 아닌지 확인
2. 행의 개수 N 확인
3. 모든 행의 열 개수가 N인지 확인

## 8.2 패턴과 필터 크기 검증

패턴과 필터가 각각 정상적인 정사각형이어도 서로 크기가 다르면 MAC 연산을 할 수 없습니다.

```text
Pattern : 5x5
Filter  : 13x13
```

따라서 `validate_same_size()`로 두 행렬의 크기가 같은지 확인합니다.

JSON 모드에서는 추가로 pattern key의 크기와 실제 행렬 크기가 같은지도 확인합니다.

```text
pattern key = size_13_1
실제 Pattern = 13x13인지 확인
```

# 9. 라벨 정규화

JSON 데이터에서는 같은 의미가 서로 다른 문자열로 표현될 수 있습니다.

```text
filter key : cross, x
expected   : +, x
```

프로그램 내부에서는 다음 두 라벨을 표준으로 사용합니다.

```text
Cross
X
```

정규화 규칙은 다음과 같습니다.

| 외부 데이터 | 내부 표준 |
|---|---|
| `+` | `Cross` |
| `cross` | `Cross` |
| `Cross` | `Cross` |
| `x` | `X` |
| `X` | `X` |

예를 들어 JSON의 expected가 `+`이면 `normalize_label()`을 거쳐 `Cross`로 바뀝니다.

```text
+
    -> normalize_label()
    -> Cross
```

필터 key도 `normalize_filters()`에서 같은 방식으로 정규화합니다.

```text
{"cross": [...], "x": [...]}
    -> normalize_filters()
    -> {"Cross": [...], "X": [...]}
```

라벨 정규화를 하는 이유는 외부 데이터 표현과 내부 판정 로직을 분리하기 위해서입니다. 내부 로직에서는 `Cross`, `X`만 비교하면 되므로 데이터 표현 방식이 조금 달라도 안정적으로 처리할 수 있습니다.

# 10. epsilon과 부동소수점 비교

두 MAC 점수 차이가 매우 작을 때는 동점으로 처리합니다.

```python
abs(score_a - score_b) < EPSILON
```

현재 코드에서 `EPSILON`은 다음 값입니다.

```python
EPSILON = 1e-9
```

`1e-9`는 다음과 같습니다.

```text
1e-9 = 0.000000001
```

두 점수의 차이가 `0.000000001`보다 작으면 사실상 같은 값으로 보고 `UNDECIDED`를 반환합니다.

## 10.1 왜 `abs()`를 사용하는가?

두 값을 빼면 순서에 따라 양수 또는 음수가 됩니다.

```text
1 - 2 = -1
2 - 1 =  1
```

동점 판정에서 중요한 것은 어느 쪽이 앞에 오느냐가 아니라 두 점수 사이의 거리입니다. 그래서 절대값을 사용합니다.

## 10.2 왜 `==`만 사용하지 않는가?

Python의 `float`는 실수를 2진수로 저장합니다. 일부 10진수 소수는 정확하게 표현되지 않기 때문에 아주 작은 오차가 생길 수 있습니다.

예를 들어 다음 계산은 수학적으로 0.3이지만 Python에서는 다르게 보일 수 있습니다.

```python
0.1 + 0.2
```

```text
0.30000000000000004
```

MAC 계산에서도 두 점수가 사실상 같지만 다음처럼 아주 조금 다르게 나올 수 있습니다.

```text
0.9
0.8999999999999999
```

따라서 단순히 `score_a == score_b`만 사용하지 않고 epsilon 기반 비교를 적용했습니다.

## 10.3 왜 1e-9인가?

`1e-9`가 모든 프로그램에서 절대적으로 맞는 값은 아닙니다. 데이터 크기, 필요한 정밀도, 문제 조건에 따라 허용오차는 달라질 수 있습니다.

이번 프로젝트에서는 아주 작은 부동소수점 차이 때문에 Cross 또는 X가 잘못 선택되는 것을 막기 위한 동점 판정 정책값으로 `1e-9`를 사용했습니다.

# 12. FAIL 원인 분석

FAIL이 발생하면 단순히 실패 개수만 확인하지 않고 원인을 나누어 확인합니다.

## 12.1 데이터 또는 스키마 문제

다음과 같은 경우 정상적인 테스트를 수행할 수 없습니다.

- `filters`가 없음
- `patterns`가 없음
- 패턴에 `input`이 없음
- 패턴에 `expected`가 없음
- `size_N_index` 형식이 잘못됨
- 해당 크기의 필터가 없음
- Cross 또는 X 필터가 없음

이 경우 해당 케이스를 실패로 기록하고 다음 케이스로 넘어갑니다.

## 12.2 행렬 크기 문제

다음과 같은 경우 MAC 연산을 수행하지 않습니다.

```text
Pattern : 5x5
Filter  : 13x13
```

또는 pattern key와 실제 배열 크기가 다를 수도 있습니다.

```text
pattern key = size_13_1
실제 Pattern = 5x5
```

이 경우 검증 단계에서 실패 사유를 기록합니다.

## 12.3 수치 비교 문제

Cross와 X 점수가 epsilon 범위 안에서 거의 같으면 `UNDECIDED`로 판정합니다.

```text
Cross Score = 0.9
X Score     = 0.8999999999999999
```

이 경우 expected가 Cross 또는 X라면 결과가 일치하지 않으므로 FAIL이 됩니다.

즉 FAIL은 항상 코드 오류를 의미하지 않습니다. 데이터 문제, 스키마 문제, 크기 문제, 라벨 문제, 수치 비교 정책 때문에 발생할 수 있습니다.

# 13. 성능 측정 방법

성능 측정에는 Python 표준 라이브러리의 `time.perf_counter()`를 사용합니다.

```python
start = time.perf_counter()

for _ in range(repeat):
    calculate_mac(pattern, filter_data)

end = time.perf_counter()
```

측정 흐름은 다음과 같습니다.

```text
측정 시작
    -> calculate_mac() 10회 반복
    -> 측정 종료
    -> 총 실행 시간 계산
    -> 반복 횟수로 나누기
    -> 초 단위를 ms 단위로 변환
    -> MAC 1회 평균 실행 시간 반환
```

현재 반복 횟수는 다음 상수로 관리합니다.

```python
PERFORMANCE_REPEAT = 10
```

한 번만 측정하면 CPU 상태, 운영체제 스케줄링, 다른 프로그램 실행 상태의 영향을 크게 받을 수 있습니다. 그래서 같은 MAC 연산을 10회 반복한 뒤 평균 시간을 계산합니다.

성능 측정에는 `input()`, `print()`, JSON 파일 읽기 시간은 포함하지 않습니다. 이번 성능 비교의 목적은 행렬 크기에 따른 순수 MAC 계산 시간 변화를 확인하는 것이기 때문입니다.

# 15. 시간복잡도 O(N^2)

MAC 연산은 이중 반복문으로 구현되어 있습니다.

```python
for row in range(size):
    for col in range(size):
        score += pattern[row][col] * filter_data[row][col]
```

바깥 반복문은 N번 실행되고, 안쪽 반복문도 각 행마다 N번 실행됩니다.

```text
N * N = N^2
```

따라서 N x N 행렬 하나에 대한 MAC 연산량은 N^2입니다.

| 행렬 크기 | N^2 |
|---|---:|
| 3x3 | 9 |
| 5x5 | 25 |
| 13x13 | 169 |
| 25x25 | 625 |

현재 MAC 구현의 시간복잡도는 다음과 같습니다.

```text
O(N^2)
```

N이 2배가 되면 연산량은 단순히 2배가 아니라 약 4배가 됩니다. 예를 들어 5x5는 25개 위치를 계산하지만 10x10은 100개 위치를 계산합니다.

실제 실행 시간은 Python 인터프리터, CPU 캐시, 운영체제 상태, 현재 시스템 부하의 영향을 받기 때문에 N^2 비율과 완전히 동일하게 증가하지 않을 수 있습니다. 그래도 행렬 크기가 커질수록 처리해야 하는 위치 수가 N^2로 증가한다는 점은 명확합니다.

# 17. 10줄 이상 결과 리포트

1. 이 프로그램은 Python 반복문으로 MAC 연산을 직접 구현한 Mini NPU Simulator이다.
2. MAC 연산은 같은 위치의 패턴 값과 필터 값을 곱한 뒤 그 결과를 누적하는 방식이다.
3. 사용자 입력 모드에서는 3x3 필터 A, 3x3 필터 B, 3x3 패턴을 입력받아 A/B/UNDECIDED를 판정한다.
4. JSON 분석 모드에서는 `data.json`의 5x5, 13x13, 25x25 패턴을 자동으로 분석한다.
5. `data.json`에 없는 3x3 성능은 코드에 정의된 기본 3x3 Cross/X 패턴으로 함께 측정한다.
6. JSON의 `cross`, `x`, `+` 같은 외부 표현은 `Cross`, `X`로 정규화하여 비교한다.
7. 패턴과 필터가 정상적인 N x N 행렬인지 먼저 검증한 뒤 MAC 연산을 수행한다.
8. 패턴 key의 N과 실제 행렬 크기가 다르면 실패 사유를 기록하고 해당 케이스를 건너뛴다.
9. 두 MAC 점수 차이가 `1e-9`보다 작으면 부동소수점 오차 가능성을 고려하여 `UNDECIDED`로 판정한다.
10. JSON 테스트 결과는 expected와 실제 decision을 비교하여 PASS 또는 FAIL로 출력한다.
11. 성능 측정은 `time.perf_counter()`를 사용하며 MAC 연산을 10회 반복한 평균 시간을 사용한다.
12. 측정 구간에는 입력, 출력, JSON 파일 읽기 시간이 포함되지 않고 순수 MAC 계산 시간만 포함된다.
13. 3x3, 5x5, 13x13, 25x25의 연산량은 각각 9, 25, 169, 625이다.
14. N x N 행렬의 모든 위치를 한 번씩 계산하므로 MAC 연산의 시간복잡도는 O(N^2)이다.
15. 실제 실행 시간은 실행 환경에 따라 달라질 수 있으므로 README의 성능값은 실행 후 직접 기록한다.
